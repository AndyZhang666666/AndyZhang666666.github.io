说完成了，还要查它真的做了什么。

用十个原创工单场景，把工具回执、数据库状态和最终回复放在一起检查。超时后核对原操作，避免重复写入。

体验 Demo ↗返回作品集

公开为程序执行记录回放；本地 API / SQLite 可复现，真实模型需另行配置与验证

要解决的问题

工具没有返回成功，是否应该再提交一次？

写入可能已经成功，只是回执丢失。只看回复文本，会把“说完成”当成完成，或者在结果未知时重复提交。批准也必须对应具体参数，不能成为任意写入的通行证。

独立设计任务、工具权限、批准流程、幂等操作与状态检查；实现 Python API、SQLite 记录、程序策略对照和前端回放，AI 辅助开发。公开材料均为原创虚构工单。

方案与取舍

回执、业务效果和回复是三份不同的证据。

只评最终回复

容易忽略实际没有执行、重复执行或越权的情况。

超时就重新提交

不知道原操作是否已提交，重复动作可能带来第二次业务效果。

核对状态后再恢复

采用的做法：保留原操作标识，查最终状态，再决定是否需要重试或接管。

把判断变成机制

  1. 批准绑定具体变更

    服务端检查角色、目标工单、参数与预期版本。批准后换参数，不能沿用原来的授权。

  2. 结果未知，先查原操作

    写入后超时场景中，恢复策略查询同一 operation_id，发现已提交后不再重复写入。公开首页展开的是已有程序记录。

  3. 把完成判定落到最终状态

    判定同时检查处理组、工单状态、记录数、权限事件和回复。基础策略在超时后停在 unknown；它的数据库也已写入，差异在于是否完成核对。

验证、代价与下一步

公开可回放十个虚构场景的基础 / 恢复策略记录，并查看事件与最终数据。写入后超时样例保留一次业务提交、一条新增记录，工单仍打开；这是程序运行的结果，不是大模型测评成绩。

公开回放方便免配置查看，但不能替代重新执行。本地 API 可复现工具效果；真实模型适配器仍需配置和实测，不能把程序策略差异写成模型能力提升。

先用独立用例覆盖重试、重复请求、取消与批准参数变化，再在同一权限和工具条件下接入模型，核对失败类型、成本与接管率。
