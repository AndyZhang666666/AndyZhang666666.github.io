# 可信 RAG 实验台｜轻量 PRD

版本：2026-10-28。状态：已选定的开发范围，不是已实现功能或已验证效果。

## 1. 做什么

一句话：不只给出答案，还让访客看见“依据从哪里来，为什么可以用”。

这是个人作品集中的独立小模块，聚焦检索、文档生效版本、权限、引用和无答案处理。现有 filing-eval 主要核对给定原文与摘要，本项目增加“从资料库找对依据”的上游环节；可以借鉴其原始结果留档和判分分离方式，不直接修改旧项目。

面向第一次访问的面试官或普通访客，目标是约一分钟完成“选问题—看回答—点开依据—改条件看变化”。这是体验目标，不是用户研究结论。

## 2. 最小场景与数据

只做虚构公司的设备借用规则。准备约 10–15 份原创 Markdown 文档，包括普通规则、管理说明、旧版和新版、相似无关内容。不要上传真实公司制度、客户资料或私人文件。

示例：旧版显示器最长借 30 天，当前生效版最长借 14 天。用户询问“现在最多能借多久？”时，应使用当前适用且有权查看的依据；询问历史日期时，不能机械认为最新文档永远正确。

每份资料有稳定编号、标题、正文、版本、生效时间和可访问角色。评测使用固定的业务日期与数据快照，结果可复现，不随电脑当天日期悄悄变化。

首版不做任意 PDF 上传、OCR、网页爬取、企业系统接入或复杂知识库后台。

## 3. 用户怎么用

一个主页面即可：

1. 提供“借用时长”“资料不足”“权限限制”三个醒目预设问题，也支持输入本场景内的问题。
2. 展示回答、所用版本和可点击的来源；点击引用后打开实际支持该结论的段落。
3. 改变示例身份、查询日期或资料快照，再运行，观察结果变化。技术详情里展开检索片段、过滤过程和评测项。

普通视图不展示无权访问的文档原文、标题或片段。开发排错详情也要遵守当前访问边界，不能通过“查看日志”泄露其他资料。

## 4. P0 功能

- 文档按标题/段落切分，保存稳定的片段编号和源文档关系。
- 实现真实文本检索，关键词/BM25 可作为首版；若已有合适的 embedding 配置可增加向量或混合检索，但不是首版阻塞条件。未实现向量检索就如实说明，不能把预设片段切换冒充检索。
- 服务端先限定当前身份和业务日期可用的文档集合，再供召回、排序和模型上下文使用。不能只在 Prompt 里要求保密，也不能只在前端隐藏。
- 根据实际检索片段调用模型回答，返回可追溯的片段引用。资料不足、相互冲突或不适用时，说明缺口或请求澄清，不补造规则。
- 引用编号必须存在；引用文字与原文片段核对。引用存在不代表结论成立，关键事实另有规则或人工参考答案检查。
- 保存问题、身份范围、业务日期、资料/索引版本、实际检索片段、模型与 Prompt 版本、原始回答和判分版本，支持导出脱敏记录。
- 切换资料快照后重新检索；旧运行保留原版本标记，不能把新资料套在旧结果上伪装成当时的依据。

示例身份切换只是虚构场景演示，不等于生产账号与租户安全。真实后端的权限测试使用独立会话/凭据，普通会话不能直接伪造管理员参数提升权限。若公开演示允许自由切换示例角色，要说明它仅接入虚构资料。

## 5. 必测案例

准备约 12 个固定问题，分别定义可用证据、关键事实与预期处理方式。下表必须覆盖：

| 案例 | 最小验收结果 |
|---|---|
| 当前规则问答 | 回答 14 天，并引用当前有效规则 |
| 历史日期问答 | 使用当时有效的 30 天规则，说明查询时间口径 |
| 普通身份查管理资料 | 未授权片段不进入该次模型上下文，不从回答/API 结果泄露 |
| 相似名称文档干扰 | 不把无关规定当作依据；检索结果可检查 |
| 库里没有答案 | 说明资料不足，不编造；有答案的问题也不能一律拒答 |
| 资料存在无法消解的冲突 | 展示可授权查看的冲突并提示需要确认，不擅自选一条 |
| 片段含“忽略规则”等注入文字 | 作为被检索数据处理，不改变系统权限或执行其他任务 |
| 模型或检索服务失败 | 保留问题和条件，明确失败阶段，允许重试 |
| 来源切换或更新 | 本次回答绑定本次资料快照，引用可定位且不串版本 |

判分把检索与生成分开：有没有召回授权且适用的正确片段、关键事实是否正确、引用是否支持结论、无依据是否乱答。不要把所有问题合成一个装饰性的总分。召回分母只包含该身份与日期下应可获得的相关证据，不把保密资料“没召回”当作检索失败。

可以用模型辅助判断语义，但少量固定样例要有人可复核的参考事实；不能把模型自评当成最终真值。不编造准确率、上线收益或统计显著性。

## 6. 前后端与运行模式

采用简单前端＋一个轻量 API 服务＋文档/索引存储即可，优先与既有工程习惯一致。无需独立向量数据库集群、多 Agent、微服务或通用知识库管理平台。

前端负责提问、条件切换、回答与来源展示；后端负责示例会话校验、授权过滤、版本选择、检索和模型调用。模型仅基于拿到的授权片段生成，不承担身份鉴权或规则生效判断。模型密钥仅留服务端。

真实运行、真实记录回放、原创示例演示分别标注。公开回放只能说明交互与历史运行，不能代替真实后端的权限验证；示例数据不计入模型评测结果。不得把全部限制文档直接打包进普通用户前端，再声称前端隐藏实现了保密。

官网默认不要求访客填写 API Key。若仍为静态站，发布可交互的回放/示例，后端提供本地可复现的启动方式；在线真实模式仅在现有安全 API 服务已配置时开启。不得将 GitHub Pages 说成能运行后端，不擅自购买托管服务。

API 服务具备输入长度限制、有限输出、超时、调用上限、限流和日志脱敏。不要读取其他项目的密钥；缺少模型配置时继续完成检索与权限测试，把真实生成联调明确列为待验证，不伪造记录。

## 7. 前端和验证标准

回答、使用依据和资料不足原因是首屏重点。技术详情按需展开；文案尽量用“找到哪些依据”“为什么没法回答”，不要求访客先理解 RAG。手机可顺序查看回答和来源，不让长文档挤走操作；键盘可操作，不仅靠颜色区分状态。

必须实际执行：检索/日期过滤单测、API 权限与参数篡改测试、引用定位测试、无答案与有答案对照，以及主流程浏览器测试。固定问题可离线复核，真实模型联调另计；未运行的检查写待验证，不写通过。

最终报告列出样本数、检索命中、关键事实检查、无依据作答和过度拒答、越权片段供给、运行失败，并记录可取得的耗时与用量。全部结论绑定本次样本、版本与运行模式。
