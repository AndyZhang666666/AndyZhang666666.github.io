# 第二轮：协商不是把底线调低

## 核心判断

“没有共同候选”只给结论不够；直接替用户放宽预算又越权。这轮把中间层补上：可解释的自愿建议 → 无副作用预演 → 本人确认 → 全员重新表态 → 带走决定。建议的精确性来自当前虚构候选和规则，不来自所谓 AI 洞察。

## 状态合同

1. `voluntaryPlans` 在克隆状态中尝试预算上界，仅返回能解锁候选的本人预算变化。已知价格、本人已确认、全员已提交、当前无交集是前提；忌口、位置和排除菜系不动。
2. `prepareVoluntaryDraft` 重新检查建议 ID 与饭局版本；只改草稿预算，其他未确认草稿保留。若草稿已有其他改动，预演按整份草稿算，不承诺只改预算。
3. `previewConditions` 复制原状态重算，返回前后最多三个展示候选和失效提醒。草稿修改使旧预演消失；真实确认才递增版本并清票。
4. 3–5 位有效模拟成员共同确认同一候选才生成决定单。新成员、条件、候选变化使旧决定失效；不能导出过期决定。
5. 导出只含公共候选、版本、模拟确认人数与核实清单，不含原话或逐人条件。不会订位、邀请或发消息。

## UI 取舍

保留原生表单、角色切换和公开虚构标识；当前进度优先，非主任务的过程计数折叠；窄屏不再用固定角色栏遮挡内容。初始画面展示三种真实不同的顾虑而不是空白营销区，主入口只有一个。

## 下一步需要真实验证，而不是直接加功能

先验证朋友能否区分“填草稿”“预演”“确认”，以及预算建议是否让人感到被施压。真实多人版本需后端权限与服务端删除；没有这些，不把本机角色切换当真实协商。不报告未经研究的耗时收益。

## 本地证据

2026-10-24：28 项 Node 测试通过；保留的全流程 Chrome 测试通过；跨两个产品的 V2 浏览器验收通过，覆盖预演不改票、导出内容、3–5 人、四种宽度及零脚本异常。最终线上复验另记，不将本地通过当发布成功。
