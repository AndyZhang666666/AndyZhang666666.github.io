# Agent 执行评测台｜轻量 PRD

版本：2026-10-28。状态：已选定的开发范围，不是已实现功能或已验证效果。

## 1. 做什么

一句话：让访客看到，Agent 说“完成了”，不代表它真的把事情做对了。

这是个人作品集中的独立小模块。已有 creative-eval / llm-output-eval 主要评内容质量；本项目评工具执行、最终数据状态和失败恢复。可以借鉴原项目的批量执行、原始结果留档、Bad Case 和报告方式，不直接改旧项目，也不沿用剧本评分维度。

面向第一次访问的面试官或普通访客，目标是不用看文档，在约一分钟内完成“选案例—看执行—看差异”。这是体验目标，不是已有用户数据。

## 2. 最小场景

只做内部工单沙盒，所有工单、规则和身份均为原创虚构数据。不接真实企业系统。

示例任务：“把 T102 转给售后组，添加一条跟进记录，但不要关闭工单。”

首版三个工具足够：查询工单、提交工单变更、查询操作状态。业务写入真实发生在隔离的测试数据库中；模型通过工具执行，不能只返回一段预设成功话术。

预期结果：处理组正确、状态未关闭、跟进记录恰好新增一次、操作有授权、最终回复与实际状态一致。

## 3. 用户怎么用

一个主页面，不做复杂后台：

1. 选择“正常执行”“写入后超时”“缺少信息”“权限不足”等案例。
2. 点击“运行案例”或“观看回放”，在执行记录中看到工具请求、返回结果和状态变化。
3. 查看基础版与加固版的结果；点开“为什么这样判”，看具体检查项，而不只是总分。

默认呈现案例、执行结果和一句解释。原始事件、版本信息、Token、耗时等放在可展开的“技术详情”里，不把一屏日志甩给访客。不展示或伪造模型隐藏思维链。

## 4. P0 功能

- 原创案例集约 10 条；至少覆盖下表，每次运行隔离数据，避免上一案例污染下一案例。
- 基础版与加固版共享模型、任务、初始数据和故障条件。两者策略差异写清楚，不能故意硬编码基础版失败。
- 服务端业务鉴权始终生效，不为制造对比效果关闭安全检查。模型的越权尝试和实际越权写入分开记录。
- 加固版支持操作标识、写入状态查询、有限重试、必要的人工确认及持久化运行状态。
- 一个操作标识重复提交相同动作不重复写；绑定不同参数则拒绝。涉及确认的动作必须绑定具体参数；工单版本变化后重新检查，不沿用过期批准。
- 执行中断后可以恢复；写入结果未知时先查状态，不能换一个新操作标识盲目重写。
- 依据最终数据库状态和事件判定结果。模型评语可作解释，不作是否成功的唯一证据。
- 保存原始运行记录与判分版本，支持离线重算判分、导出一次运行的脱敏 JSON。

| 案例 | 最小验收结果 |
|---|---|
| 正常执行 | 分组正确、工单未关闭、记录新增一次 |
| 缺少目标组或工单号 | 提示补充，不猜测、不写入 |
| 身份没有修改权限 | 不产生业务写入；越权尝试可见 |
| 查询工具短暂失败 | 有限重试，达到上限后明确失败 |
| 数据库已写入但响应超时 | 查询原操作状态；不重复添加记录 |
| 重复点击或提交 | 同一已确认动作最多产生一次业务效果 |
| 写入前取消 | 停止未开始的变更，不显示已完成 |
| 工单版本在确认后变化 | 重查或提示冲突，不覆盖新数据 |

取消不能承诺撤销已经生效的操作；此时展示已发生的效果，只停止尚未开始的步骤。回放只读，不再次产生写入；重新运行使用新的隔离案例环境。

## 5. 前后端与运行模式

优先沿用已核实的工程习惯，采用简单前端＋一个轻量 API 服务＋SQLite 或等价事务存储即可。无需微服务、队列、通用工作流编辑器和多 Agent。

前端只负责输入、确认、展示；授权、参数校验、去重和状态更新由服务端承担。模型适配层独立，不能把服务商密钥写进网页或仓库。接口明确区分：待补充、待确认、运行中、成功、失败、拒绝和结果未知；失败保留案例与运行标识，允许安全恢复。

三种模式必须分别标注：

- 真实运行：后端调用已获授权的模型并实际操作测试数据库。
- 真实记录回放：播放真实留档的工具事件和结果，保留模型、版本、时间等来源；不伪装为当场生成。
- 示例演示：没有真实运行记录时使用原创示例，明确标注，不计入模型评测结果。

公开官网默认无需密钥即可体验回放或示例；真实后端必须可在本地启动。若现有官网仍为纯静态部署，不把后端塞进 GitHub Pages，也不擅自开通新的付费托管。在线真实模式只有在已有安全后端配置可用时启用，并具备调用上限、限流、超时、输入限制和日志脱敏。

不得读取其他项目凭据或认证存储。缺少可用模型配置时，继续完成规则、界面与离线测试，把真实模型联调单列为待验证，不伪造真实运行报告。

## 6. 验证与呈现

至少报告：任务总数、成功数、运行失败数、越权尝试及实际写入、重复写入、人工接管，以及能从真实记录取得的耗时和调用用量。总任务成功率不能静默排除超时和解析失败；缺失用量写“未知”。不填预估提升百分比，不凭少量样本宣称生产级可靠。

必须实际执行：工具/规则单测、API 集成测试、重复提交与恢复测试、主流程浏览器测试。模型评测和不调用模型的程序测试分开。所有通过项要有执行记录，未运行不能算通过。

前端验收：桌面和手机可完成同一核心流程；窄屏改用分段或切换查看，不丢失对照内容；按钮能用键盘操作；状态不只靠颜色表达；错误能读懂并能继续；页面无明显横向溢出，主要操作不被长日志挤走。

## 7. 交付与 GitHub

建议公开体验路径为 /agent-bench/，源码和后端放在独立项目目录，具体适配当前官网结构。不要改旧评测项目、简历和其他作品。

交付代码、此 PRD 的最终版本、简短 README、测试报告、演示截图和脱敏运行样例。README 说清场景、架构、核心取舍、启动步骤、运行模式和已知限制。提交依赖锁文件和配置示例，不提交密钥、真实用户资料、运行中的数据库或未审查原始日志。

按真实阶段提交文档、功能、测试修复和官网接入，正常推送到已核对的本人仓库；不伪造日期、空堆提交或强推。完成时列出分支、commit、远端核验结果，以及是否合并主分支、是否部署、是否验证线上交互，不能把这几件事混为一谈。

与另一个 RAG 项目并行时使用独立工作目录与分支，优先只改自己的目录。修改官网公共入口前先获取远端最新版本，只增量添加本项目；保留对方及既有改动，冲突不能整文件覆盖。不为了方便重构官网。

## 9. 不做什么

首版不做真实工单接入、外发消息、支付、复杂账号系统、长期记忆、多模型路由和通用 Agent 平台。先把一个可运行、可解释、可复查的小闭环做好。
